# Техническое задание

## Проект: BitrixText Forge

**Версия документа:** 1.0  
**Актуально для версии приложения:** 0.1.0

## 1. Назначение

BitrixText Forge — локальное настольное приложение для подготовки сообщений Bitrix24. Пользователь редактирует исходный текст в Markdown и получает текст, оформленный совместимым подмножеством BBCode Bitrix24, либо обычный текст без разметки.

Приложение не подключается к Bitrix24, не отправляет сообщения и не хранит учётные данные. Итог предназначен для ручного копирования и вставки в интерфейс Bitrix24.

## 2. Цели и границы продукта

### 2.1. Цели

- ускорить подготовку структурированных сообщений;
- сохранить Markdown как формат редактирования;
- обеспечить предсказуемое преобразование в поддерживаемую разметку;
- показать результат и диагностические сообщения до копирования или экспорта;
- сохранять черновики, настройки, шаблоны и список последних файлов локально.

### 2.2. Вне области версии 0.1.0

- Bitrix24 REST API, авторизация, отправка или обновление сообщений;
- генерация тегов `[img]`, `[timestamp]` и `[disk]`;
- диалоги для вставки изображений, timestamp и файлов Bitrix24.Drive;
- гарантия подсветки синтаксиса внутри `[code]` в Bitrix24;
- поддержка тегов `[send]`, `[call]`, `[put]`, `[context]` и `[chat]`.

Теги и поведение Bitrix24 могут различаться между интерфейсами. Приложение не заменяет проверку итогового сообщения в целевом интерфейсе.

## 3. Технологии и платформы

### 3.1. Стек

- Rust stable, edition 2024;
- `eframe` 0.36 и `egui` 0.36;
- `pulldown-cmark` 0.13 для разбора Markdown;
- `serde` и `serde_json` для локальных данных;
- `rfd` для нативных файловых диалогов;
- `arboard` для системного буфера обмена;
- `directories` для определения стандартного каталога данных;
- `anyhow` и `thiserror` для обработки ошибок;
- `vergen-gitcl` для сведений о сборке.

Точные версии зависимостей фиксируются в `Cargo.lock`.

### 3.2. Платформы

- Windows — основная целевая платформа;
- Linux и macOS — поддерживаются возможностями `eframe` при наличии совместимого окружения.

## 4. Пользовательские сценарии

Приложение позволяет пользователю:

1. создать новый документ или открыть Markdown-/текстовый файл;
2. отредактировать Markdown в основном редакторе;
3. выбрать профиль преобразования;
4. получать результат автоматически или по команде конвертации;
5. просмотреть итоговый BBCode, визуальное preview и диагностику;
6. вставить поддерживаемые специальные конструкции через диалоги;
7. скопировать итог в системный буфер обмена;
8. сохранить исходный документ, экспортировать результат или JSON-представление;
9. применить встроенный или пользовательский шаблон;
10. продолжить работу из восстановленной локальной сессии.

## 5. Интерфейс

### 5.1. Главное окно

Главное окно содержит:

- верхнюю панель с командами нового документа, открытия, сохранения, экспорта, копирования результата, выбора профиля, шаблонов и настроек;
- редактор исходного Markdown;
- область результата с вкладками `BBCode`, `Preview`, `Диагностика` и `Спецвставки`;
- строку состояния с информацией о документе, преобразовании и ошибках операций;
- возможность включить синхронную прокрутку редактора и области результата.

### 5.2. Режим преобразования

- При включённой автоконвертации результат обновляется после изменения исходного текста или настроек рендеринга.
- При выключенной автоконвертации пользователь запускает преобразование явной командой.
- Ошибки чтения, записи, экспорта и обращения к буферу обмена показываются в интерфейсе и не должны завершать приложение аварийно.

### 5.3. Спецвставки

Через модальные диалоги пользователь может вставлять в Markdown:

| Конструкция | Поля и проверка |
|---|---|
| `[u]...[/u]` | текст; пустое поле заменяется значением по умолчанию |
| `[user=ID]...[/user]` | обязательный ID и отображаемое имя |
| `[size=N]...[/size]` | текст и размер от 8 до 30 px; доступны пресеты |
| `[color=#HEX]...[/color]` | текст, палитра RGB и HEX из 3 или 6 символов |
| `[icon=URL ...]` | обязательный URL, необязательные `size` и `title` |

Диалог не вставляет некорректные параметры в документ: пользователь получает понятное сообщение о причине ошибки.

## 6. Входные форматы

### 6.1. Markdown

Парсер принимает:

- абзацы и мягкие/жёсткие переносы строк;
- заголовки уровней 1–6;
- жирное начертание, курсив и зачёркивание;
- ссылки;
- inline-код и fenced code block;
- цитаты;
- маркированные и нумерованные, включая вложенные, списки;
- изображения;
- горизонтальные линии;
- task list;
- таблицы Markdown;
- inline HTML с безопасными эквивалентами BBCode: `b`/`strong`, `i`/`em`, `u`, `s`/`del`/`strike`, `a href` и `br`.

Для расширений, не имеющих гарантированного представления в выходном профиле, создаются диагностические сообщения или применяется fallback.

### 6.2. BBCode-подобные вставки

После разбора Markdown приложение распознаёт следующие конструкции в текстовых узлах:

- `[u]...[/u]`;
- `[user=ID]...[/user]`;
- `[color=#RGB]...[/color]` и `[color=#RRGGBB]...[/color]`;
- `[size=N]...[/size]`, где $8 \le N \le 30$;
- `[icon=URL ...]`.

HEX-цвет нормализуется к нижнему регистру и форме с `#`. Некорректные цвет и размер не переносятся в итоговую разметку: содержимое сохраняется как текст, а в диагностику добавляется предупреждение.

### 6.3. Неподдерживаемый ввод

- неподдерживаемые HTML-теги передаются как обычный текст с предупреждением;
- теги `[send]`, `[call]`, `[put]`, `[context]` и `[chat]` не распознаются как разметка и не генерируются приложением.

## 7. Внутренняя модель

Преобразование строится на AST, а не на цепочке строковых замен.

### 7.1. Блоки документа

Модель поддерживает `Paragraph`, `Heading`, `Quote`, `CodeBlock`, `List`, `Image` и `HorizontalRule`. Список хранит признак нумерации, начальный номер и вложенные элементы; изображение — URL, alt-текст и необязательный размер.

### 7.2. Inline-узлы

Модель поддерживает текст, жирное и курсивное начертание, подчёркивание, зачёркивание, ссылки, упоминания пользователей, цвет, размер, иконки, изображения, inline-код, мягкие и жёсткие переносы.

Соседние текстовые узлы объединяются перед поиском BBCode-вставок. Это обеспечивает корректное распознавание тега, если Markdown-парсер разделил его на несколько событий.

## 8. Профили вывода

### 8.1. Bitrix24 Full Message

Основной профиль для BBCode с расширенным форматированием.

| Входная сущность | Результат |
|---|---|
| жирный текст | `[b]...[/b]` |
| курсив | `[i]...[/i]` |
| подчёркивание | `[u]...[/u]` |
| зачёркивание | `[s]...[/s]` |
| ссылка с отличающимся текстом | `[url=URL]текст[/url]` |
| ссылка, равная URL | `[url]URL[/url]` |
| цвет | `[color=#hex]...[/color]` |
| размер | `[size=N]...[/size]` |
| иконка | `[icon=URL ...]` |
| упоминание | `[user=ID]имя[/user]` |
| inline-код | `[color=#6b7280][b]...[/b][/color]` |
| заголовок | `[b]...[/b]` с необязательной обёрткой `[size=N]` |
| цитата | `>>` в начале каждой строки или блок между `------` |
| список, включая task list | текстовые маркеры и отступы по 4 пробела; состояние задачи сохраняется как `[ ]` или `[x]` |
| таблица | ASCII-сетка с ровными колонками; заголовок оформляется доступным тегом `[b]` |
| горизонтальная линия | настраиваемая текстовая строка |
| code block | `[code]...[/code]` без подсветки синтаксиса (Bitrix24 её внутри тега не поддерживает) |
| изображение | BBCode-ссылка на URL с alt-текстом, если он есть |

Для изображения формируется информационная диагностика, поскольку `[img]` не используется текущим профилем. Блоки отделяются пустой строкой. Единственный стиль переноса — реальный `\n`.

### 8.2. Bitrix24 Core Safe

Консервативный профиль сохраняет базовые теги `[b]`, `[i]`, `[u]`, `[s]`, `[url]` и переносы строк.

- Заголовки становятся жирным текстом без `[size]`.
- Цвет и размер отбрасываются с сохранением содержимого и предупреждением.
- Иконки и изображения превращаются в текстовые ссылки с предупреждением.
- Inline-код сохраняется обычным текстом.
- Списки выводятся текстовыми маркерами; для ненумерованного списка применяется выбранный маркер.
- Code block по умолчанию выводится с отступом 4 пробела; при включённом параметре `safe_allow_code` оборачивается в `[code]...[/code]` (без подсветки синтаксиса).

### 8.3. Plain Text

Профиль не создаёт BBCode и сохраняет читабельную структуру:

- ссылки выглядят как `текст (URL)`;
- цитаты получают префикс `>`;
- код получает отступ 4 пробела;
- изображения представляются как `alt: URL` или URL;
- списки и горизонтальные линии остаются текстовыми.

### 8.4. Manual Code Highlight

Профиль использует Full renderer с режимом ручного оформления кода. Code block не оборачивается в `[code]`: каждая строка получает префикс `>>` (визуальное выделение, как у цитаты) и отступ в 4 пробела. При включённой опции `manual_code_colors` токены дополнительно оборачиваются в документированный `[color=#HEX]` по языку блока (`csharp`/`rust`/`python`/`js`/`sql`/`php` и т.д.); это лишь приближение подсветки в GUI и не является гарантией подсветки синтаксиса в Bitrix24.

## 9. Настройки

Настройки хранятся локально и включают:

- профиль по умолчанию;
- включение автоконвертации и синхронной прокрутки;
- светлую или тёмную тему;
- размер шрифта редактора и результата;
- размеры `[size]` для H1–H6: `0` означает только `[b]`, ненулевые значения ограничены диапазоном 8–30;
- размер изображения по умолчанию (`small`, `medium`, `large`);
- маркер ненумерованного списка: `•` или `-`;
- стиль цитаты: построчный `>>` либо блок `------`;
- текст горизонтальной линии;
- предупреждения о потере форматирования;
- настройки ручной подсветки кода;
- включение и интервал автосохранения от 5 до 300 секунд;
- альтернативный каталог хранения;
- цветовые и размерные пресеты для диалогов.

## 10. Предпросмотр и диагностика

### 10.1. Preview

Вкладка preview отображает AST-документ визуально в интерфейсе приложения. Это представление служит для проверки структуры и оформления перед переносом результата в Bitrix24. Оно не является эмулятором рендеринга Bitrix24.

### 10.2. Диагностика

Диагностические сообщения имеют уровни `Info`, `Warning` и `Error`, дедуплицируются и выводятся на отдельной вкладке. Диагностика сообщает, в частности, о:

- недопустимом цвете или размере;
- преобразовании списка в текстовые маркеры;
- fallback для изображения и code block;
- неподдерживаемой таблице или HTML;
- невозможности открыть, сохранить, экспортировать документ или скопировать результат.

## 11. Файлы и локальное хранение

### 11.1. Пользовательские файлы

- Открытие: `.md`, `.markdown`, `.txt`.
- Сохранение исходника: текст Markdown.
- Экспорт результата: текстовые файлы `.txt` и `.bbcode.txt`.
- JSON-экспорт содержит поля `markdown`, `bbcode` и `profile`.

### 11.2. Служебные данные

По умолчанию данные располагаются в каталоге, вычисленном `directories::ProjectDirs` для `com/BitrixTextForge/BitrixText Forge`; пользователь может задать иной каталог.

| Файл | Содержимое |
|---|---|
| `settings.json` | настройки приложения |
| `session.json` | исходный Markdown, выбранный профиль и путь текущего файла |
| `autosave.md` | автоматически сохранённый черновик |
| `templates.json` | пользовательские шаблоны |
| `recent.json` | до 10 последних файлов в порядке от новых к старым |

При запуске приложение пытается восстановить сохранённую сессию. Ошибки локального хранения должны быть обработаны без аварийного завершения.

## 12. Шаблоны

Шаблон содержит имя, категорию, Markdown, кэш результата BBCode, список переменных вида `{{имя}}`, дату изменения и признак системного шаблона.

Встроенные шаблоны:

- «Важное сообщение»;
- «Сообщение со ссылкой»;
- «Сообщение с кодовым блоком»;
- «Сообщение с изображением»;
- «Упоминание сотрудника».

Пользователь может фильтровать шаблоны по имени или категории, вставлять шаблон в редактор, сохранять текущий документ как пользовательский шаблон и удалять пользовательский шаблон. Системные шаблоны не удаляются.

## 13. Архитектура

Кодовая база разделена на следующие модули:

| Модуль | Назначение |
|---|---|
| `app` | состояние приложения, интерфейс, вкладки, диалоги и preview |
| `parser` | Markdown и встроенные BBCode-конструкции → AST |
| `model` | модель документа, размеры изображений и валидация |
| `render` | рендереры Full, Core Safe и Plain Text |
| `profiles` | профили и параметры рендеринга |
| `diagnostics` | структурированные сообщения диагностики |
| `settings` | сериализуемые настройки приложения |
| `storage` | локальные JSON-данные, автосохранение и файловые операции |
| `templates` | модели и встроенные шаблоны |
| `highlight` | вспомогательное представление кода в preview |

Публичная библиотека экспортирует эти модули и сведения о версии сборки; бинарный crate запускает `eframe`-приложение.

## 14. Обработка ошибок и ограничения

Приложение обязано сохранять работоспособность при:

- ошибках чтения и записи файлов;
- некорректном JSON локальных данных;
- недоступности системного буфера обмена;
- некорректных URL, цветах, размерах и параметрах специальных вставок;
- неполном или нестандартном Markdown;
- документах с Unicode, кириллицей и смешанными языками.

HTML и скрипты не исполняются. При невозможности сохранить форматирование renderer предпочитает сохранить читаемый текст и добавить диагностику.

## 15. Нефункциональные требования

- Приложение локально и не требует сетевого доступа для основной работы.
- Интерфейс не должен блокироваться при обычном редактировании и конвертации.
- Конвейер Markdown → AST → результат должен обрабатывать документ размером не менее 100 KB за время, приемлемое для интерактивной работы.
- Конвертация должна быть детерминированной для одинакового исходного текста, профиля и настроек.
- Все пользовательские данные и настройки сериализуются в UTF-8 JSON либо UTF-8 текст.

## 16. Тестирование и критерии приёмки

### 16.1. Тестирование

Проект содержит unit- и интеграционные тесты для:

- разбора Markdown и специальных BBCode-вставок;
- валидации размера 8–30 и HEX-цветов из 3 или 6 символов;
- каждого профиля рендеринга;
- ссылок, заголовков, цитат, списков, горизонтальных линий, изображений и кода;
- исключённых тегов, которые не должны появляться в сгенерированном выводе;
- сериализации настроек, сессии и шаблонов;
- лимита и дедупликации недавних файлов;
- Unicode и документа более 100 KB;
- smoke-проверки preview без паники.

### 16.2. Критерии приёмки

Версия 0.1.0 соответствует ТЗ, если:

1. запускается настольное приложение Rust с GUI на `egui`/`eframe`;
2. пользователь может открыть, создать, отредактировать и сохранить Markdown-документ;
3. доступны профили Full Message, Core Safe, Plain Text и Manual Code Highlight;
4. Full profile генерирует `[b]`, `[i]`, `[u]`, `[s]`, `[url]`, `[color]`, `[size]`, `[icon]`, `[user]` и `[code]` согласно внутренней модели;
5. для изображений используется описанный текстовый fallback с диагностикой, без генерации `[img]`;
6. Plain Text не содержит сгенерированного BBCode;
7. специальные диалоги валидируют пользовательский ввод;
8. доступны preview, диагностика, копирование в буфер, экспорт и шаблоны;
9. работают автосохранение, восстановление сессии и история максимум из 10 последних файлов;
10. автоматические тесты `cargo test` проходят успешно.

## 17. Краткое описание продукта

BitrixText Forge — автономный Markdown-редактор и конвертер для подготовки сообщений Bitrix24. Он использует AST для предсказуемого преобразования, предлагает несколько профилей вывода, локальные шаблоны и сохранение состояния, а также явно сообщает о случаях, когда форматирование заменено безопасным текстовым представлением.
